# 面试官角色与流程

## 角色、重点与岗位分别确定

生成入口见 [生成前的两问](intake.md)。角色决定评价视角，重点决定本轮内容与深度，岗位决定需要胜任的工作；三者不能互相代填。

不保存适用于所有使用者的“技术负责人、前端转全栈”默认身份。已在本轮对话明确的角色、岗位和重点可以复用；新一轮依照入口规则确认。候选人上一份职位或简历文件名不能证明面试官角色。

## 按角色改变问题

| 角色 | 评价视角 | 问法 |
| --- | --- | --- |
| 直属技术负责人 | 独立交付、技术取舍、UI 判断、协作、AI 验证、成长空间 | 让候选人走完一条真实需求，解释决策、失误和验收 |
| 未来同事／同级工程师 | 实现、接口协作、代码质量、调试、审查和交接 | 从亲自负责的模块、一次跨模块协作或故障开始 |
| 跨团队协作方 | 接口约定、依赖、信息同步、异常处理与推进 | 追一次有分歧或依赖阻塞的实际交付，核实双方边界 |
| 架构或平台负责人 | 系统边界、数据一致性、权限、规模、成本、演进 | 用已知业务限制追问方案成立条件，不默认高并发 |
| 创始人或业务负责人 | 用户价值、优先级、交付速度、风险与技术协作 | 用自然语言解释业务结果和取舍，技术细节仅作核验 |
| HR 或招聘负责人 | 经历、动机、职责真实性、协作、岗位预期 | 使用可理解的证据问题；保留少量技术核实题并给简明解释 |

角色变化要影响主问题、观察角度和解释方式；重点决定深入哪些内容与时间分配，只修改标题不算适配。领导也可以重点考技术，HR也可以要求技术核实，不能按身份擅自改成泛管理题或取消技术深度。级别变化也要调整：初级关注实施与学习，中级关注完整模块和取舍，高级关注跨模块边界与持续结果。

## 按考察重点改变内容

| 本轮重点 | 应追到的具体内容 |
| --- | --- |
| 技术深度与工程能力 | 算法和机制、实际配置、选择与替代、故障证据、调优及效果验证 |
| 项目真实性与个人贡献 | 接手状态、亲自产物、协作分工、关键决策、真实失败、验收与成果口径 |
| 学习能力与学习方法 | 一次陌生任务的知识差距、资料渠道、实验、失败纠正、验证与迁移，避免只问“平时怎么学” |
| AI开发工具与工作流 | 近期真实交付、上下文、工具选择、输出不满意的定位、代码/界面检查与可复用方法 |
| UI、设计与产品判断 | 用户目标、信息层级、具体视觉改动、状态、响应式、交互和实现取舍 |
| 协作、责任意识与推进 | 接口和责任边界、评审反馈、阻塞、分歧、交接及实际推进结果 |

多个方向允许自然语言排序，例如“技术为主、学习其次”，不用强制百分比或限制只能选择一项。学习方法、协作等开放题给可观察的过程和证据锚点，不编造统一事实答案。

## 可执行的 60 分钟安排

以下是已明确“前端/UI岗位、技术负责人视角、技术与AI开发为重点”的场次示例，不是所有使用者的默认设置。其他岗位与重点应重排环节；专题讨论先给充分题库，现场再按时间选择。

| 环节 | 分钟 |
| --- | ---: |
| 定向自我介绍 | 3 |
| 公司、团队、角色、贡献边界 | 6 |
| 最近项目的两条深挖主线 | 22 |
| UI 或岗位场景 | 8 |
| AI 开发方式 | 12 |
| 求职原因与期望 | 3 |
| 公司介绍 | 2 |
| 候选人反问 | 4 |
| 合计 | 60 |

项目环节可以安排四张题卡，例如 6、5、6、5 分钟，总计 22 分钟。题卡中的追问按回答择用，不要求每条都问。扩展到 75 分钟时把新增时间明确分给项目或现场任务。30 分钟则减少核心题与场景规模，明确本轮未覆盖能力，不能把 60 分钟原稿标成 30 分钟。

先给每张核心题标注岗位能力和本轮重点，再检查覆盖。对于上述前端/UI示例，前端实现、UI与工程交付占主要技术时间；明确要求Agent专项时则以专项为准。若某人没有AI应用开发声明且岗位不要求，就用AI编程与学习题，不强加知识库架构考试。

12 分钟 AI 模块可按以下安排覆盖用户关心的内容：近期真实任务 4 分钟，串联使用工具、有效上下文、不满意时的定位和可复用方法；从零做项目 4 分钟；最近亲测技术与学习渠道 2 分钟；个人应用 1 分钟；总结可迁移工作流 1 分钟。细节追问占用该模块时间，不再额外叠加。

## 开场与背景

“请用三分钟介绍最近两段经历，重点讲你最擅长独立交付什么，以及一个个人贡献最大的项目。”

围绕最近公司问产品、用户、团队构成、汇报关系、分工、谁做决策、谁验收。把“团队完成”“本人实现”“接手已有能力”“使用现成模板”分清。

项目时间跨公司时中性询问关系和职责变化；多个项目并行时核实复用、投入与实际范围。任期短、项目数量多、经历重叠都需要解释，不能单独作为造假证据。

## 求职与公司介绍

问本次找工作的优先事项、上一份工作的离开原因、希望延续或改变的工作方式、当前岗位与长期方向是否匹配。事实题没有统一标准答案，不替候选人填写原因。

公司介绍只使用已知信息，可按以下字段组织：

“我在团队负责【面试官职责】，这个岗位主要与【协作对象】配合。我们服务【用户】，解决【问题】；团队有【人数及分工】。近期主要工作是【当前职责】，后续会涉及【未来职责】。前一到三个月希望完成【具体目标】。我们通过【已确认的协作与验收方式】推进工作。”

未确认字段明确待补，不写成事实。结尾保留候选人了解产品、团队、工作方式、岗位期望和待遇的时间；不能仅凭反问话题判断积极性。

## 共同 UI 场景

下面是前端/UI岗位的可选场景；在本轮岗位与考察重点相关时使用：

“设计一个 AI 任务管理页，包含筛选、任务列表、详情、批量重试与导出。任务有排队、运行、成功、失败状态。先补问必要需求，再给出布局或草图，说明组件划分和第一步实现。可以使用 AI。”

八分钟内主要观察需求和判断，不宣称已验证完整编码交付。若安排实际编码，单独给出时间与环境。

参考答案看用户目标、操作优先级、信息层级、间距与对齐、列表密度、空/加载/失败/权限状态、响应式、键盘操作，以及操作状态与任务规则的关系。布局可以不同，需要有理由。

一个合理答案可以是：顶部放主要筛选和创建入口，列表突出任务名、状态、更新时间和可执行操作，详情在侧栏展示进度与错误；失败状态提供有条件的重试，批量操作显示选择数量与适用范围，窄屏调整详情布局。也可以采用独立详情页，依据是信息密度与操作频率。合格是结构清晰、状态完整、能解释操作规则；加分是主动发现视觉、可访问性、状态竞态和实施成本的关系。八分钟草图不能代替运行页面验收。

追问“AI 生成的页面能用但不好看，你具体改哪三处？”要求指出可观察的问题、修改方式和验证结果，避免只说更简洁、更高级。
